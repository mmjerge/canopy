# Contributing to Canopy

Thanks for your interest in contributing. This guide covers the development setup
and the workflow the project uses.

## Development setup

Canopy uses [uv](https://docs.astral.sh/uv/) and a `src/` layout. Install the package
with the dev tooling:

```bash
uv sync --extra dev
# or, with plain pip:
pip install -e ".[dev]"
```

Optional feature extras (install as needed):

- `plot` — `matplotlib`, for the demos that render charts.
- `llm` — `boto3`, for Amazon Bedrock (`canopy.llm.BedrockClient`).
- `openai` — `openai`, for `canopy.llm.OpenAIClient` (set `OPENAI_API_KEY`).
- `bench` — `boto3` + `datasets`, for demos that pull a real benchmark (MMLU, GSM8K).

Install the git hooks once so checks run on every commit:

```bash
pre-commit install
```

## Running checks locally

CI runs the same checks; you can reproduce them all locally:

```bash
pre-commit run --all-files          # black, flake8, mypy, file hygiene
ruff check src tests examples       # linting
mypy                                # type checking (config in pyproject.toml)
pytest --cov=canopy --cov-branch    # tests + coverage
```

The CI coverage gate is `--cov-fail-under=90` (the suite currently sits around 93%).
Please keep new code covered.

## Branching and pull requests

- The default branch is **`dev`**; it is protected and requires CI to pass.
- Branch off `dev`, using a descriptive prefix: `feat/...`, `chore/...`, `docs/...`,
  `fix/...`.
- Open your pull request **against `dev`**. The PR template includes a short
  verification checklist.
- All required checks (`lint` and the `test` matrix on Python 3.10–3.12) must pass
  before a PR can merge. Squash-merge is preferred to keep history tidy.
- `main` is reserved for release-ready snapshots.

## Style and conventions

- Formatting is enforced by **black** (line length 100); linting by **flake8** and
  **ruff**; typing by **mypy**. Match the surrounding code's style and type hints.
- Keep imports at module top level; reserve in-function imports for genuinely lazy or
  optional dependencies (e.g. `boto3`, `openai`, `matplotlib`).
- Prefer clear docstrings that explain *why*, consistent with the existing modules.
- Don't commit generated artifacts (chart PNGs, `.npz` caches, coverage files); they
  are git-ignored and regenerated by running the demos.

## Commit messages

Conventional-style prefixes are used (`feat:`, `fix:`, `chore:`, `docs:`, `ci:`,
`refactor:`, `style:`). Keep the subject under ~72 characters and use the body to
explain the what and why.
